# Template install checklist (v3.8.1)

PhanesLight works through this list during Phase 2.5 Step 4 when it fetches the script template library, and mirrors the outcome of every item into the bootstrap session summary. This file ships pinned to the template version, so the checklist and the scripts can never fall out of step.

Provenance note: the scripts in this library take no path substitution. Each script finds the project by walking up from the current directory until it sees `.phaneslight/config.json`, and every path it uses is relative to that root. There is nothing to adapt, which is the whole point: a value that is never substituted is a value that can never be substituted wrong.

## Items

1. Platform detected. Only the matching variant set is fetched and installed; the other platform variant is not written into the project. The cross-platform `cli.js` dispatcher (v3.2) is fetched and installed on **every** platform (it is in both the `windows` and `posix` arrays of the manifest's `phaneslight` dispatcher entry).
2. Every fetched file passes a sanity check before it lands. For every stamp-carrying file that means the stamp comment `# phaneslight-template v3.8.1 <name>` (or `rem phaneslight-template v3.8.1 <name>` for the `.cmd` shim) appears within the first two lines, after the shebang on POSIX or after `@echo off` in the `.cmd` shim. **The settings fragment is the one exception, and it is a structural one, not an oversight:** it is pure JSON and can carry no comment, so its check is that it parses and carries a `hooks` key. A 404 body or an HTML error page must never be written into `.phaneslight/scripts/`.
3. Manifest version equals this run's own line 1 stamp version. On a mismatch, treat it as a fetch failure and fall back to generating the scripts from the phaneslight.md Step 4 and Step 4b specifications.
4. Files install into `.phaneslight/scripts/` keeping their variant extension (`.ps1` and `.cmd` on Windows, `.sh` on POSIX; `cli.js` on both). The platform dispatcher maps `<name>` to the platform file; the cross-platform `cli.js` forwards to it, so agents invoke `node .phaneslight/scripts/cli.js <name>` in any shell. The settings fragment references the filenames that carry the extension.
5. POSIX only: the executable bit is set on every installed script by `install-templates`.
6. `.phaneslight/config.json` is written before the first script runs. Scripts read it at invocation, so a missing config is each script's defined error case, reported cleanly, not a crash.
7. Smoke run inside the project via the cross-shell entry: `node .phaneslight/scripts/cli.js module-list` and `node .phaneslight/scripts/cli.js register-check` both exit 0 (proving `cli.js` forwards to the platform dispatcher). Optionally, `node .phaneslight/scripts/cli.js anchor-check` also exits 0, proving the same forwarding for the v3.8.0 node program (it is advisory by default, so a stale-anchor report never fails the smoke run). Each hook script, fed a minimal tool call JSON on stdin, exits 0 on the pass through case, and each also exits 0 at once when run with no piped input (stdin is a terminal), never blocking. On both platforms this covers the v3.4 `hook-ledger-status` alongside the other two.
8. The platform settings fragment is merged into `.claude/settings.json`. Existing hooks are preserved, never overwritten. The Step 4b read back verification then passes: every PhanesLight hook command contains `.phaneslight/scripts/` and contains no drive letter and no leading slash. **(v3.4)** Both platform fragments additionally carry a `SessionStart` group invoking `hook-ledger-status`, which ships on both platforms as of v3.8.0.
9. The `config.json` `templates` block is written: `{ "version": "3.8.1", "source": "fetched" }`, or `"generated"` when the fallback path produced the scripts.
10. Any script genuinely edited for this project is recorded in the session summary with the reason. The default is zero edits.
11. Prompt templates (v3.3): the manifest `promptTemplates` group is fetched on **every** platform (no variants) and installed to each entry's `installPath` under `.claude/template/` (`agent-definition.md`, `report.md`, and **(v3.4)** `readme-docs.md`, `readme-tests.md`, `doc-header.md`, the blocks `scaffold` writes), each passing the same sanity check with the stamp form `<!-- phaneslight-template v3.8.1 <name> -->` within the first two lines. On an update run an installed prompt template whose sha256 no longer matches the `.phaneslight/manifest.json` record is user-customized: preserved, never overwritten, recorded in the session summary. **(v3.4) A preserved file is additionally checked for a stale reason.** The install holds the staged replacement template at that moment, so it compares that template's sha256 against the `templateSha256` the manifest recorded at install time. Equal means preserve silently, as before. Different means the upstream template has moved on since the user customized theirs: preserve the edit anyway, the rule is unchanged, and print one advisory line naming the file and both versions so the user can judge whether the reason to customize still holds. This is advisory only and never changes the exit code. A manifest written before v3.4 carries no `templateSha256`, so those entries stay UNKNOWN and no staleness is claimed for them; a guessed baseline would produce a false all-clear, which is worse than an admitted unknown. On fetch failure the Phase 4 Template Contracts in phaneslight.md are the fallback: `.claude/template/report.md` and the agent definitions are authored from the contracts, and the retry is recorded, exactly as with the scripts.
12. **Falsification, `hook-stamp-guard` honours an explicit `stampedTrees` (v3.8.1).** With `.phaneslight/config.json` carrying `"stampedTrees": ["documentation","tests"]` and `"modules": ["vendor"]`, and a real `vendor/` directory the project does not want stamped, a `Write` tool call creating `vendor/new.md` with no stamp **MUST NOT** be denied: the guard exits 0. The same call creating `documentation/new.md` with no stamp **MUST** be denied with exit 2. An explicit `stampedTrees` is the authoritative list plus `docRoot`; `modules` extends the DEFAULT list only, never an explicit one, and `docRoot` is appended either way. Both platforms **MUST** return the same exit code for both calls. The `file_path` in the tool call must be ABSOLUTE: a relative path exits 0 on both ports before any tree is consulted, which reads as a false pass.
13. **Falsification, `doc-check` audits dated FILES and freezes dated FOLDERS (v3.8.1).** A 600-line document with no DOC header at `<docRoot>/plans/2026-01-01_x.md` **MUST** be reported as both `OVER-CEILING` and `NO-DOC-HEADER`. The same file inside a dated FOLDER, `<docRoot>/architecture/2026-01-01_snapshot/y.md`, **MUST NOT** be reported at all, and neither must one under `session-summaries/` or under a `frozen_classes` folder. A frozen class is a folder; a file's own name never freezes it. Both platforms **MUST** print the same offender set after `tr -d '\r'`; the ORDER differs between the ports (`find` against `Get-ChildItem -Recurse`) and is not part of the contract.
